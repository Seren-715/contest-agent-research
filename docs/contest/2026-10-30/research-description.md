# 赛题 1「科研助手」参赛者说明文档

云端运行时限（2026-10-24）：A/B 每题 540 秒，C/D/E 每题 900 秒，包含模型、工具、自检与实验等待。D 实验执行/RPC/客户端等待分别为 840/870/880 秒，受单题总预算约束。运行结束后平台继续完成请求排空、抓包封存与判题；“协议有效”只表示输出协议检查通过，不等于裁判和证据归档已完成。平台故障显示待核查或待补评、成绩为空，不记为选手 0 分。

> 2026 CCF 网络大会 · 第一届全国高校 Agent 网络创新挑战赛
>

## 1. 文档定位

本文件面向赛题 1 参赛者，说明科研助手 Agent 的任务目标、五类题型、输入输出协议、论文证据要求、复现提交规则、评分组成、独立复核和安全边界。

题目的正式输入由平台通过一次派题记录发送。平台先生成 `dispatch.json`，再将其中11 个 `case_id` 对应的题目放入 `data/<队伍名>/assigned/`。Agent 只读取 `assigned/` 中的题目，并逐题处理 `case_id`。题目 JSON 中的 `case_id`、`function`、`title`、`input`、`materials`、`constraints`、`expected_output` 和 `output_schema_ref` 是本题唯一任务依据。字段定义和完整 JSON 示例以包内 `参赛者文档/Agent输入输出格式规范.md` 为准；本文件解释参赛者必须遵守的工程规则和评分口径。本文所有相对路径均以联调包根目录为起点。

本版说明派题文件输入、文档读写与定位能力、提交预检查和目录权限。参赛者负责生成本队 JSON、Markdown 和图片，并保留实际实验产物；平台负责判题和专家复核。

正式题目、论文集合、冻结评分金标、模型接口、时间片和配额以平台公告为准。本文示例中的编号、论文和数值只用于说明格式，不代表正式答案。

## 2. 赛题目标

参赛者需要设计并打包一个科研助手 Agent，使其能够从本地论文库和题目材料中完成科研对话、文献检索、文献综述、论文复现和研究 Idea 升华，并提交可校验的结构化结果。

核心要求是：

- 只使用题目允许的材料和平台接口；
- 事实、数字、方法归因和引用能够追溯到指定论文；
- 区分论文已报告结果、题目提供的模拟观察和本次实际运行结果；
- 按当前 `case_id` 返回正确 JSON，不输出额外自然语言包装；
- 对无法核验、无法运行或材料缺失的情况如实报告，不猜测、不伪造。

## 3. 任务类型

五类题型的名称保持不变，按 1-3-2-3-2 分配独立测试案例，总计 11 套；五类题型、七个评分项和各类案例数量是三个不同维度。

| 类型                   | 编号  | Agent 主要工作       | 题数 | 单题客观满分               |
| -------------------- | --- | ---------------- | ---: | --------------------:|
| Chat                 | A-* | 科研回答与澄清          | 1 | 5                    |
| Literature_Retrieval | B-* | 本地论文检索与匹配理由      | 3 | 15                   |
| Survey               | C-* | 带引用的 Markdown 综述 | 2 | 25（事实 15 + 引文 10）    |
| Reproduction         | D-* | 实验执行、指标与图表       | 3 | 40（流水线 20 + 数据图表 20） |
| Idea                 | E-* | 可验证研究方案          | 2 | 15                   |

每套案例独立执行，题号、输入、评测依据各自独立。Agent 只处理本轮派题记录中的题目。

## 4. Agent 核心功能要求

### 4.1 任务解析和协议校验

Agent 应先解析题目 JSON，确认 `case_id`、`function`、允许材料、约束和输出格式。不得根据文件名、标题或旧题目自行补全未提供的材料。提交前应检查 JSON 可解析、字段类型正确、`case_id` 匹配当前题目，以及所有要求的文件路径确实存在。

### 4.2 论文检索和证据管理

Agent 应在允许的论文目录中使用完整且唯一的 PDF 文件名。检索结果按相关性排序，每篇论文提供具体匹配理由，并排除纯营销、无关推荐、纯视觉识别或其他不符合题意的论文。不得凭标题猜测论文内容，不得返回本地不存在的文件名。

对于综述和 Idea，建议维护“论文—事实—页码—报告段落”的证据关系。正文中的事实、数字和方法归因必须有指定论文支持；不能把一篇论文的方法、数据或实验数字转移到另一篇论文。

### 4.3 综述生成

Survey 报告应比较研究问题、任务定位、方法、数据、指标、结论和局限，形成技术脉络，而不是简单拼接论文摘要。正文至少 800 个字符，使用 `[编号]` 或 `[编号, p.页码]` 标注事实和数字，结尾必须有 `## 参考文献`，列出实际引用的至少 5 篇指定论文及完整 PDF 文件名。

### 4.4 论文复现

Reproduction 必须区分材料发现、环境配置、代码执行、运行证据和结果对比。只有实际运行且结果可追溯时才能使用 `status: completed`。无法实际核验时使用 `materials_missing` 或 `failed`，指标值使用 `null`，不得从 PDF 猜测实测结果。题目要求的指标必须恰好输出三项；生成的每张图必须真实存在并有 `path`、`caption`、`x_label`、`y_label` 和 `legend`。所有图片统一保存在 `data/figure/<战队名字>/` 下，`figures[].path` 使用相对于项目根目录的路径，例如 `data/figure/选手1/D-01-result.png`。图片文件名和扩展名没有固定要求，但路径必须位于本队 `data/figure/<战队名字>/` 内，不能使用绝对路径或 `..` 跳出项目目录。

三项指标的精确名称、单位、运行环境和提交要求已写入本题 `input`，无需另外读取指标说明文档。论文、数据和冻结脚本仍以本题允许材料为准。

### 4.5 Idea 研究方案

Idea 报告应明确研究问题、已有方法局限、核心技术路线、基线、数据集、实验设计、消融、量化指标、文献互补关系、可行性、失败边界和可证伪方式。题目给出的模拟观察只能作为待验证现象，不能改写成论文结论或已完成的改进实验。

### 4.6 文档读取、定位与写入（必备能力）

参赛 Agent 必须具备文件操作和文档检索能力，不能只接收一段提示词后返回文本：

1. **读取**：解析 UTF-8 JSON、Markdown 和文本，读取允许的 PDF 正文；遇到扫描版 PDF 时，在允许工具和资源内进行 OCR，无法解析时报告材料问题。
2. **定位**：先读取本队 `dispatch.json`，按 `case_ids` 和 `cases[].question_file` 定位 11 个 `assigned/` 题目；按题目的完整 PDF 文件名、相对路径和正文关键词检索材料，并记录可核验的章节或页码。不能凭文件名猜测论文内容。
3. **写入**：在允许目录内创建所需子目录，写入11 个结果 JSON、C/E Markdown 和 D 类图表；本队实验代码、缓存和中间产物放入本队工作子目录（例如 data/<队伍名>/work/）。JSON 和 Markdown 使用 UTF-8 编码。
4. **回读校验**：写入后重新读取文件，核对 JSON 可解析、题号匹配、文件非空、Markdown 与 JSON 正文一致、图表路径存在；成功写入前不得报告完成。
5. **受限访问**：只读派题记录、已派题目和允许材料，只写本队产物。不得修改题目，访问其他队伍或平台内部目录，或使用绝对路径、`..`、符号链接绕过授权范围。
6. **异常处理**：材料缺失、文件重名或权限不足时，保留可见错误并按平台渠道反馈，不选择题目未授权的替代材料。D 类用 `materials_missing` 或 `failed`，无法核验的指标使用 `null`；其他题型保持原有 Schema，不增加自定义错误字段。

接入验收要求见 [Agent输入输出格式规范.md](Agent输入输出格式规范.md) 的“文档能力与目录权限验收”。

## 5. 统一输入协议

平台生成本队 `dispatch.json`，并将 A、B、C、D、E 分别 1、3、2、3、2 套独立案例放入本队 `assigned/`。Agent 按 `case_ids` 和 `cases[].question_file` 读取对应题目，不自行抽题或扫描未派发题目。

派题记录至少包含：`dispatch_id`、`team`、`selection_mode`、`case_ids` 和每题的 `question_file`。

```json
{
  "case_id": "C-99",
  "function": "Survey",
  "title": "当前题目标题",
  "input": "当前任务说明",
  "materials": ["允许使用的材料"],
  "constraints": ["必须遵守的约束"],
  "expected_output": "输出要求摘要",
  "output_schema_ref": "Survey"
}
```

输入对象不包含参考答案、内部评分金标或其他选手结果。Agent 只读取本轮授权的材料。

## 6. 五类输出协议

每次派题包含 A、B、C、D、E 分别 1、3、2、3、2 道题，共 11 道题。Agent 必须生成 11 个独立的 JSON 结果文件，结果保存到本队目录根部；派发题目位于 `assigned/`，不能复制为结果：

```text
data/<战队名字>/assigned/<case_id>.json   # 只读题目
data/<战队名字>/<case_id>.json            # Agent 结果
```

以下仅列每类一个文件，实际还需保存派题记录中剩余 6 个结果：

```text
data/选手4/A-01.json
data/选手4/B-01.json
data/选手4/C-01.json
data/选手4/D-01.json
data/选手4/E-01.json
```

文件名中的 `case_id` 必须与 JSON 内的 `case_id` 以及题目中的 `case_id` 完全一致。Survey 和 Idea 的完整 Markdown 文件仍按各自规则另存到 `data/expert`。

完整逐题字段见 [Agent输入输出格式规范.md](Agent输入输出格式规范.md)。

## 7. 评分口径

| 评分项    | 满分   | 对应题型                     |
| ------ | ----:| ------------------------ |
| 聊天类    | 5 分  | A / Chat                 |
| 检索类    | 15 分 | B / Literature_Retrieval |
| 综述事实类  | 15 分 | C / Survey               |
| 引文溯源类  | 10 分 | C / Survey               |
| 要点覆盖类  | 15 分 | E / Idea                 |
| 实验流水线类 | 20 分 | D / Reproduction         |
| 数据与图表类 | 20 分 | D / Reproduction         |

七个评分项满分合计 100 分，映射沿用上述五类题型。

自动打榜成绩满分 100 分，只由客观判题产生，占最终综合成绩的 70%。专家评分与 Token 消耗评分独立复核，合计占最终综合成绩的 30%，不参与初赛自动排行榜。复核内部权重目前留空，待负责人确认；不能默认两项各占 15%。

按 1-3-2-3-2 分配独立测试案例，总计 11 套。每题先按其适用评分项计分，再计算类别平均：`S_i = sum(s_ij) / N_i，N_A/N_B/N_C/N_D/N_E = 1/3/2/3/2`。例如 B 类三题得分为 10、12、14 时，平均分为 12。A/B/C/D/E 类单题及类别平均上限分别为 5、15、25、40、15 分，自动打榜成绩为五类平均分之和，等价于七个评分项在适用类别内的平均分之和，不再归一化。

最终综合成绩为 `0.7 × 自动打榜成绩 + 0.3 × 复核部分折算成绩`，两部分均以 0～100 分计。例如 80 与 90 合成为 83。复核结果不覆盖客观原始分或自动榜分；复核未完成或内部权重未确认时，综合成绩为 `null`。

每套案例保留原始证据分、映射后的单题分、运行状态及错误。选手答题失败、超时或非法输出按本题规则计分；裁判模型、平台实验服务或证据归档失败不判为选手 0 分，本轮暂不生成完整成绩，保留原产物等待核查或补评。D 类v3依据可信执行证据独立计分；D-05实际完成的条件可保留部分分，总指标不可核验仍为null。尚未返回结果且未收到终止状态的案例为 `pending` / `running`，不得忽略它或用已完成案例平均生成完整榜分。派题身份、题目哈希或额外结果文件异常会阻止本轮进入榜单。

### 客观计分依据

1. **聊天类（5 分）**：合法 JSON `answer` 得 3 分， `clarifying_question` 得 2 分，沿用现有字段检查。
2. **检索类（15 分）**：去重后令 H 为命中的相关论文数，N 为冻结相关论文数，U 为未命中冻结相关集合的论文数，`max(0, min(15, 15H/N - 0.75U))`。文件名仅字母大小写不同时按同一篇论文匹配和去重；其他字符须与完整文件名一致。重复论文不重复加分。
3. **综述事实类（15 分）**：冻结 K 项事实，C 为正确覆盖数，F 为严重事实错误数，`max(0, min(15, 15C/K - 3F))`。沿用冻结事实与逐项证据判定。
4. **引文溯源类（10 分）**：冻结引用位数 M，V 为正确匹配引用位数，H 为引用幻觉数，`max(0, min(10, 10V/M - 2H))`。增加重复引文不改变分母。当前判题依据提交文本和冻结候选事实；原文 PDF 页级金标核验仍需平台补齐，不能把模型的页码判断视为已完成原文核验。
5. **要点覆盖类（15 分）**：研究动机、技术路线、实验设计、基准数据集、量化评价指标各 1.5 分；复现瓶颈反思、多文献互补机制各 3 分；场景可行性与落地约束 1.5 分。未覆盖项不加分，保留判定证据。
6. **实验流水线类（20 分）**：D-01/D-02/D-05使用layered-d-v3的实际输入、基线、候选、产物、条件覆盖、复跑与边界七类分项，按D类实验要求计分，不使用旧8个等权检查点。
7. **数据与图表类（20 分）**：D-01/D-02/D-05按可核验指标6、实验效果10、真实图表4计分；具体数学口径及部分分见D类数据与图表判分规则.md。

D 类底层保留原有 10 分证据量表，服务器适配器映射到上述 20 分上限，每项只映射一次。各项最低 0 分，最高为表列满分；不适用于本题的项不加分。

### 独立复核

专家原始记录合计上限 30(创新功能，综述以及idea升华报告，token使用)。创新扩展须有真实实现及可复核证据。专家必须填写评语与审核信息，参赛者不提交评分文件。

初赛仅按 `automatic_leaderboard_score` 排名。综合成绩单独保存为 `composite_score`。同分处理与同队多次有效提交选择 latest/best 等策略待平台冻结，当前不使用 Token 或专家分作初赛排序依据。

## 8. 提交流程

1. ### 8.1 流程总览与职责

   一轮打榜依次经历：公开用例调试 → 平台登记版本并派发 11 案例 → Agent 作答与提交 → 客观判题及初赛自动榜分 → 独立复核 → 条件满足后计算综合成绩 → 反馈与申诉。镜像规范由外部平台提供。

   | 环节    | 参赛者负责                             | 平台负责                    |
   | ----- | --------------------------------- | ----------------------- |
   | 准备    | 实现五类任务及文档能力，打包镜像，验证输出             | 公布接口、公开调试材料、资源配额和规则版本   |
   | 执行    | 定位本轮题目，读取允许材料，运行实验并写入本队产物         | 随机派题、提供隔离环境与模型接口、记录运行过程 |
   | 提交    | 交付11 个结果 JSON、Markdown、图片及要求的实验产物 | 收集并冻结提交版本，校验文件后评分       |
   | 复核与排名 | 提供创新功能证据，查看本队反馈                   | 专家评审、完整成绩汇总、榜单发布及争议处理   |

   ### 8.2 公开调试材料与预检查

   平台发布公开用例和格式示例，公开调试成绩不计入正式榜单。示例中的数值、引用和报告仅说明格式，不能直接充当正式答案。平台只向 Agent 提供本轮派题记录、11 道题和允许材料。

   提交前在参赛工作区根目录执行，将“你的队伍名”替换为本队目录名：

   ```powershell
   py -3 参赛者模拟\validate_submission.py 你的队伍名
   ```

   预检查检查派题和结果文件、部分字段及 Markdown 一致性，不验证论文事实、实验真实性或全部 Schema 约束。D 类未完成时仍应使用 `failed` 或 `materials_missing`，不能为使预检查通过而伪造成功。

   ### 8.3 镜像上传与版本登记

   按平台镜像规范提交 Agent 镜像及启动说明；入口、架构、服务端口、健康检查和模型接口以平台接入公告为准。镜像应包含文档解析、检索、文件写入与实验运行所需依赖，不能假设执行时可临时访问外网安装工具。

   平台登记提交版本并关联 `submission_id`。重新上传形成新版本，已登记版本用于对应轮次评测，不得在评测过程中替换程序或结果文件。上传次数、截止时间和重提交规则以公告为准。

   ### 8.4 运行环境与目录权限

   平台提供本队隔离工作区、只读题目和允许的论文材料；Agent 使用统一模型接口及本轮公开的资源配额。模型、Token 限额、时间片和超时条件以冻结接口公告为准。

   Agent 可以读取本队 `dispatch.json`、`assigned/`、允许材料及本队产物；可以写入本队结果和工作文件、本队图片，以及按命名规则划分的本队 Markdown 报告。原始题库、参考答案、内部评分资料、裁判凭据和其他队伍文件均不在授权范围内。题目与派题记录只读，路径须保持在授权范围。

   当前 D 类采用单机低资源离线协议，CPU 可执行，不要求多 GPU 集群或真实网络管理权限。直接读取本队 `assigned/<case_id>.json` 的 `input` 获取三项指标、单位和提交要求；实际执行使用本题允许的数据与冻结脚本。

   ### 8.5 随机派题与输入定位

   每次派题含 A、B、C、D、E 分别 1、3、2、3、2 套独立案例。正式一轮共 11 题；A 随机、B–E 固定，顺序按派题记录。旧版各一题模式只供调试，不产生新版完整自动榜分。

   ```text
   data/<队伍名>/dispatch.json
   data/<队伍名>/assigned/A-xx.json
   data/<队伍名>/assigned/B-xx.json
   data/<队伍名>/assigned/C-xx.json
   data/<队伍名>/assigned/D-xx.json
   data/<队伍名>/assigned/E-xx.json
   ```

   Agent 先读取 `dispatch.json` 的 `case_ids`，再按 `cases[].question_file` 定位题目。不得自行抽题、扫描未派题目或把输入 JSON 复制为答案。定位文件后仍须核对题目内部 `case_id`，每道题独立按 `output_schema_ref` 执行。

   | 类别                       | Agent 执行动作        | 必交结果字段                                         |
   | ------------------------ | ----------------- | ---------------------------------------------- |
   | A / Chat                 | 回答科研问题，提出一个关键澄清问题 | `case_id`、`answer`、`clarifying_question`       |
   | B / Literature_Retrieval | 检索允许论文库、核验正文并去重   | `case_id`、`papers`，每篇含完整 `filename` 和 `reason` |
   | C / Survey               | 比较指定论文，整理事实及引用    | `case_id`、`path`、完整 `markdown`，另存同文 Markdown   |
   | D / Reproduction         | 核验环境与材料，执行实验并生成图表 | `case_id`、`status`、恰好三项 `metrics`、`figures`    |
   | E / Idea                 | 根据论文和模拟观察提出可验证方案  | `case_id`、`path`、完整 `markdown`，另存同文 Markdown   |

   ### 8.6 文件写入与提交

   11 个 UTF-8 JSON 写入队伍目录根部，文件名和内部 `case_id` 必须与派题记录一致。以下仅列每类一个文件，实际按派题记录保存全部 11 个 JSON：

   ```text
   data/<队伍名>/A-01.json
   data/<队伍名>/B-02.json
   data/<队伍名>/C-03.json
   data/<队伍名>/D-04.json
   data/<队伍名>/E-05.json
   data/expert/C-03-综述-<队伍名>.md
   data/expert/E-05-灵感Idea报告-<队伍名>.md
   data/figure/<队伍名>/D-04-result.png
   ```

   Survey/Idea 正文至少 800 个字符，含 `## 参考文献`，JSON 正文与另存 Markdown 逐字一致。Survey 文件名严格为 `case_id-综述-队伍名.md`；Idea 文件名符合 `case_id-*Idea报告-*队伍名.md`。

   D 类图片必须实际存在，每张图包含 `caption`、`x_label`、`y_label`、`legend`。本队实验代码、缓存和中间产物放入本队工作子目录（例如 data/<队伍名>/work/），保留平台要求的真实运行产物。写入后重新读取校验，再按平台接口提交或确认作答结束。

   输出只含当前题型字段，不添加输入题目的 `function`、`title` 等字段，不添加自然语言前缀或 Markdown 代码围栏。创新功能的实现证据按平台要求单独提交，不改变五类 JSON 结构。

   ### 8.7 D 类实际运行要求

   只有实际执行且结果可追溯时才使用 `completed`。材料缺失用 `materials_missing`，运行失败用 `failed`；无法核验的指标值用 `null`，不从论文、示例或参考值推测 `observed`。

   平台根据实际运行过程核验复现流水线和实验产物。参赛者按题目要求保留命令输出、实验数据和图表，不编造成功日志，也不修改平台采集记录。论文报告值、平台公开基线值与本次实测结果须分别注明来源。

   ### 8.8 自动评分与本队反馈

   平台收集本轮结果并进行评分，参赛者通过平台查看本队分类得分、错误原因和复核状态。参赛者无需配置裁判服务或运行评分程序。

   | 反馈状态                              | 含义                                   |
   | --------------------------------- | ------------------------------------ |
   | `valid`                           | 11 案例均有终止结果，自动成绩完整；个别案例失败按 0 分且保留原状态 |
   | `incomplete`                      | 有案例未完成，自动榜分为 null                    |
   | `invalid` / `invalid_submission`  | 本轮派题身份、输入摘要或目录范围校验失败，不入榜             |
   | 复核 `pending` / `awaiting_weights` | 不影响完整自动成绩；综合成绩暂不生成                   |

   平台反馈每套案例原始状态和错误。选手超时或非法输出按本题规则计分；平台裁判失败待补评、成绩为空，不显示为选手 0 分。未完成案例等待终止结果，不能静默略过。

   ### 8.9 专家评审

   专家评审总分 100 分，按 Survey 深度、Idea 可行性、创新扩展、Token 四个维度占比 30% 进行综合评定。人工分由专家填写，参赛者提交报告与必要说明，不提交专家评分文件。

   ### 8.10 完整成绩、榜单与多次提交

   初赛使用客观自动打榜成绩，满分 100 分。专家和 Token 独立复核完成且内部权重确认后，按 70% 自动成绩 + 30% 复核折算成绩计算综合成绩。多次提交保留各版本记录，重复评审不重复计分；有效提交版本选择和同分处理待平台公告。

   ### 8.11 反馈、申诉与赛后审查

   1.平台反馈本队分类分数、复核状态、格式问题和运行失败原因。对平台异常或评分争议，按公告时限提交 `submission_id`、相关题号或报告项及问题说明，等待平台处理结果。

   组委会按公告复核代码、镜像和运行记录。禁止硬编码正式答案、预置答案报告、伪造实验、访问内部评分材料或其他队伍文件、绕过统一模型接口。合法开源依赖应注明来源；违规处理依据赛事规则和实际证据执行。

2. Agent 读取派题记录并定位 11 道题，按各题 `output_schema_ref` 执行任务。11 个题号后缀可能不同，必须以派题记录为准。

3. Agent 将11 个结果 JSON 写入本队目录根部，将 C/E Markdown 写入规定的本队报告文件，将 D 图表写入 `data/figure/<队伍名>/`，保留本队实验产物。

4. Agent 回读校验文件；参赛者执行本地预检查，修正格式或文件缺失问题。

5. 按平台提交接口交付本轮产物。服务器收集结果和运行记录，完成自动判题。

6. 平台先发布完整自动成绩；专家复核 Survey、Idea、创新扩展，另行记录 Token 评分，再按已确认规则计算综合成绩。

### 8.12 参赛者提交预检查

在联调包根目录执行，将 `你的队伍名` 替换为已存在的本队目录名：

```powershell
py -3 参赛者模拟\validate_submission.py 你的队伍名
```

该脚本检查派题记录、对应题目和结果文件、部分字段及 Markdown 一致性，不调用裁判模型。预检查通过后，仍须遵守第 11 节清单并接受正式判题；它不验证论文事实、实验真实性或全部 Schema 约束。无法完成复现时仍应如实提交 `failed` 或 `materials_missing`，该合法失败提交计 0 分并保留状态。

### 8.13 本队反馈与复核

参赛者通过平台查看本队分类得分、格式错误、运行失败原因和人工复核状态。遇到争议，按公告时限提供 `submission_id`、题号和问题说明。平台保留完整评测记录并提供经过过滤的本队反馈。

## 10. 安全与公平要求

禁止以下行为：

- 硬编码公开题答案或预置参考报告；
- 读取 `score`、其他队伍目录或内部评分金标；
- 私自调用外部模型或绕过平台统一模型接口；
- 将论文未报告的数字写成论文结论；
- 将模拟观察写成已经完成的实验；
- 提交不存在的论文、图片或 Markdown 文件；
- 通过额外 JSON 字段、自然语言前缀或损坏文件绕过 Schema 校验。

比赛结束后，组委会可对排行榜前列队伍的镜像、日志和代码进行复核。违反公平竞赛或数据隔离规则的提交按赛事规则处理。

## C/E 报告输出限制（c1-output-limits-v1）

新版派题对 C 类综述和 E 类 Idea 报告增加以下硬性上限；不改变既有评分公式、报告字段或文件保存协议：

| 类别 | 正文硬上限 | 建议 |
|---|---:|---|
| C / Survey | 5000 字符 | 约 3500 字符 |
| E / Idea | 4500 字符 | 1800～3200 字符 |

正文按 Markdown 中 `## 参考文献` 章节之前的内容计数，空格、标点和 Markdown 符号均计入；参考文献章节不计入正文上限。C 类正文中平台识别到的文中引用实例总数不得超过 40；`[1,2]` 按两个引用实例计算，正文中重复引用也分别计数，应合并同一自然段内对同一文献的重复标注。不得逐句重复挂标或堆叠多个无关文献编号。E 类不得通过程序动态拼接、硬编码扩写或套用无关的通用段落规避篇幅要求。

平台会对新版 C/E 派题执行上述上限校验。该输出限制采用独立版本 `c1-output-limits-v1`，不追溯重算旧评测。

## C/E 判题说明更新（2026-10-24）

E 类每项应写清本题材料依据、具体设计和验证办法。仅罗列“基线、消融、时延、吞吐、准确率”等词语不能替代有效实验设计或指标计算口径；正文中分散列出的指标定义可以分别作为证据。针对性还核对多文献组合接口、失效检测与具体回退、可验证的新设计；未说明的依据不由裁判补写。详见本赛题《评分规则》的“C/E 证据核查更新”。

若提示裁判证据核验未完成，平台保留已执行结果并等待补评，暂不发布不完整总分。这与 Agent 启动失败、输出格式不符不同，无需先反复上传镜像。选手提交协议和总分公式不变，历史成绩不自动重算。
